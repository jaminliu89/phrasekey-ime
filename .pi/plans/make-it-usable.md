# PhraseKey — 从 demo 到能日常用的输入法

> 计划落盘时间：2026-08-23
> 目标：让 PhraseKey 成为可以真的拿来打字的输入法，而不是 108 词的演示品。

## 现状盘点（已验证）

- `swift build` 通过，`dist/PhraseKey.app` 已构建，已安装到 `~/Library/Input Methods/`
- macOS IME（IMK）：拼音 / 小鹤双拼 / 小鹤音形 + 常用语优先 + 自学习 + 常用语面板 ✅
- iOS 键盘扩展：可加载、可弹出；闪烁已定性为免费 Apple ID 签名固有问题（上轮结论）
- **致命短板：内置词库 `Sources/PhraseKeyIME/Resources/dict.tsv` 仅 108 条**
- 次要问题：`PinyinSyllable.all` 用「声母 × 韵母」笛卡尔积生成，含大量非法音节（如 `fai`/`ruang`），影响连续拼音切分准确度

## 目标（本轮验收标准）

1. 内置词库 ≥ 10 万条，覆盖日常高频词（打「明天开会」「辛苦了」「人工智能」都必须出）
2. 引擎在 349k 级词条下**启动 < 300ms**、macOS 内存增量可接受
3. iOS 键盘扩展**不因词库变大而超内存被杀**（键盘扩展内存上限约 30-60MB）
4. 连续拼音切分正确率提升：非法音节从表里剔除
5. 有回归测试脚本，改引擎后能一键验证

## 2026-08-23 定性完成：真凶是 Info.plist 缺必需键

### 结论（已验证）
键盘扩展 `NSExtensionAttributes` **缺 `PrimaryLanguage`**（另缺 `IsASCIICapable`、`PrefersRightToLeft`）。
缺失时系统能把键盘注册进「设置→键盘」列表，但**拉起扩展进程时判定配置无效直接拒绝**。

**验证证据**：
```
$ xcrun devicectl device info processes | grep PhraseKey
46985  .../PhraseKey.app/PlugIns/PhraseKeyKeyboard.appex/PhraseKeyKeyboard
```
补键前该进程从不出现，补键后出现且用户实测键盘正常存活。

### 这解释了所有此前无法解释的现象
| 现象 | 解释 |
|---|---|
| 设置里看得见键盘 | 注册进列表只需 bundle 结构正确 |
| 切过去不出现 / 闪 | 拉起进程时配置校验失败 |
| 崩溃报告里找不到它 | 从未启动，自然没有崩溃 |
| Jetsam 里找不到它 | 同上 |
| 进程列表里 BareKBExt 在跑、它没有 | 直接证据 |

### 定位手段：空壳对照组法（本轮最大收获）
编译零依赖键盘 BareKB，**同设备/同系统/同免费 Team/同签名**，唯独代码极简。
它长期存活 → 一刀切开「环境问题」与「本项目问题」。
随后逐项 diff：先 diff 代码（发现手动 frame 布局、缺高度约束），
再 **dump 两份 Info.plist 逐键对比** → 定位到 plist 必需键缺失。

**教训：应该在做代码 diff 之前就先 diff 配置**，这一步零成本且不需要用户参与，我却放到最后才做。

### 一并修掉的真问题（非死因但必要）
1. 手动 frame 布局依赖 `keyArea.bounds`（viewDidLoad 时为 0）与 `UIScreen.main`（扩展内不代表键盘尺寸）
   → 已重写为 UIStackView 纯约束。这是用户反馈「不像完整输入法、像占位」的原因。
2. `inputView` 关掉 autoresizing 后无高度来源 → 已加 heightAnchor 268
3. 键盘包内曾打入 20 万词全量词库（实测净增 93MB，超扩展预算）→ 已换 3 万条移动版（10.6MB）
4. 引擎音节表与切分器 10 项 bug → 已修，回归全绿
5. 补齐输入法必备功能：拼音显示区、候选横滑（30 候选）、Shift、符号层、handleInputModeList

### 排序问题定性：比用户反馈的更严重

用户反馈「womenz 时『我们』排第 3」。实测发现是**排名随机**：

| 跑第几次 | 前 6 候选 |
|---|---|
| 1 | 卧 斡 窝 握 我 **我们** |
| 2 | **我们** 我 斡 卧 窝 握 |
| 3 | 斡 我 **我们** 卧 窝 握 |

候选位置随机 = 用户无法建立「背编号」的肌肉记忆，比排得不准更致命。

### 根因（两个 bug 叠加，均有对照证据）

| # | Bug | 证据 | 修复 |
|---|---|---|---|
| 1 | `min(e.freq, 999)` 硬截断词频 | dict.tsv 中 7987 条 freq>999，截断后全变 999 → score 全并列 1999。实测「我」372146 /「我们」111743 /「斡」1017，真实差 300 倍却同分 | 改对数压缩，且**降级为 tiebreak** |
| 2 | `best.values.sorted { score > }` 非全序 | Dictionary.values 遍历顺序不保证 + Swift sorted 非稳定排序。Bug 1 制造大量同分后，顺序每次进程都变 | 改全序：score → freqBonus → 词长 → text |

### 新增主排序信号：覆盖度（coverBonus）

`公共前缀长度 / 输入长度`。理由：**用户多敲一个字母就是在缩小意图范围**。
womenz（6 字母）时「我」只覆盖 wo（2）、「我们」覆盖 women（5）——
即使「我」词频高 3 倍，用户想打的显然是「我们」，否则他不会接着敲 menz。
用比例而非绝对长度，避免长输入时加成穿透 baseScore 分档。

### 修复效果（实测对照）

| 输入 | 修复前 | 修复后 |
|---|---|---|
| womenz | 我们 第 6/1/3 位（随机） | **我们 第 1** |
| niha | 泥/逆/拟… 你好 第 6 | **你好 第 1** |
| zhongguor | 肿/偅/忠… 中国 第 7 | **中国人民解放军 第 1** |
| nihaosh | — | **你好 第 1** |
| nh（简拼） | 你好 第 2 | **你好 第 1** |
| mt（简拼） | 明天 第 5 | **明天 第 3** |

查询耗时 0.037 → 0.164 ms（覆盖度计算开销），远低于人类感知阈值。

### 新增工具：候选探针

`bash Scripts/probe_query.sh womenz zhongguor` —— 打印候选顺序、score、freq、切分结果。
`--step` 逐字母展开。**排序调优必须看真实数据，不许凭感觉调。**

踩坑记录：探针最初只打印 score，导致我误判「同分 = tiebreak 没生效」，
实际是同分下 freq 已正确排序（我 841 > 握 514 > 窝 509 > 卧 464 > 斡 454）。
已改为同时打印 `[s{score}/f{freq}]`，避免再误读。

- ~~「排序质量只是好不好用，不是能不能用」~~ —— 证伪。排名**随机**属于不能用级别：
  用户建立不了肌肉记忆。排得不准可以忍，排得每次不一样不能忍。

## 2026-08-23（续二）对齐默认方案：小鹤双拼 / 小鹤音形

### 起因
用户提出「默认是小鹤双拼和小鹤音形，查仓库和 PRD 看有哪些忽略的」。
核查发现：**产品默认方案此前几乎没被测过**，前两轮修的断档与排序全部只验全拼。

`InputScheme.default = .flypy`，但回归里双拼只有 2 条断言。默认路径在盲区里。

### 本轮定性的 5 个问题（均有实测证据）

| # | 问题 | 证据 | 状态 |
|---|---|---|---|
| 1 | **双拼奇数键位全线断档** | 逐键模拟：wourfg 6 步 5 空、jqvsjl 6 步 4 空、nihc 4 步 1 空 | ✅ 已修 |
| 2 | **coverBonus 坐标系错位** | 双拼输入（womf）去比候选全拼（wo men），覆盖度与精确匹配判定全错 | ✅ 已修 |
| 3 | **encode/decode 不可逆** | `wo` → encode `wo` → decode 回 `wuo`（不存在的音节）→ 双拼回退路径查错键 | ✅ 已修 |
| 4 | **iOS 键盘硬编码 .pinyin** | KeyboardViewController:62，且切换方案不持久化 | ✅ 已修 |
| 5 | **小鹤音形无码表 → 永久空转** | `xingma.tsv` 在仓库中不存在，CodeTable.hasLoaded 恒 false | ⬜ 未解决 |

### 问题 1 详解：为什么双拼比全拼更需要 progressive
双拼每字**定长 2 键**，用户打词时必然逐键经过奇数长度。
而 `query()` 的 flypy 分支只有「精确匹配 → decode 后当全拼查」，无 progressive 回退
→ 奇数位必空。全拼上轮已补三级回退，双拼漏了。

修法：新增 `searchFlypyProgressive`
① 双拼码前缀匹配（主力）—— 奇数位末键是声母，前缀匹配天然补其韵母
② 偶数前缀成词 —— 取前 2⌊n/2⌋ 键查词
③ decode 成全拼后借用全拼 progressive

沿用上轮教训：前缀匹配必须排在「更短的已成词部分」之前。

实测修复后：nihc / womf / womfzd / mktm / vsgo / rfgsving / xbkule 全部 0 断档。

### 问题 3 详解：encode/decode 不可逆
`w` 是合法声母键 → decodeSyllable 走声母分支 → `w` + finalFor(o)=`uo` = `wuo`。
但汉语拼音里 `wo` 本身就是完整音节，`wuo` 不存在。

修：decode 结果必须过真实 417 音节表校验；不合法时回退「去掩音介音」形式
（wuo→wo、yie→ye），最后试零声母表。另补 `finalToKey` 的 `"v"` / `"üe"` 键
（音节表用 v 写 ü，如 lü→lv，缺键导致 lv/nv/lve/nve encode 出空串）。

全量 417 音节往返扫描：**403 → 410 可逆**。

剩 7 个已逐个定性（不再笼统写「固有重码」）：
- `hm` / `m` / `n` —— 叹词无韵母，双拼定长 2 键本质无法表示（方案边界，非 bug）
- `lo` / `lve` / `nve` / `rua` —— 小鹤键位重码（l 键兼 iang/uang、t 键兼 ue/üe）

均极低频，不影响日常输入。已设阈值 10（基线 7），数量上涨即回归失败。

### 我自己踩的坑（记录以免重犯）

解码出来是 `wuo/shuan/f` —— 真码是 `womfzd`。

**探针默认 scheme 是 .pinyin，测的根本不是用户默认路径。**
已给 `probe_query.sh` 加 `--flypy` / `--xing`。
