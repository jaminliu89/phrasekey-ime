### 已定性但**未修**：简拼排序缺陷（诚实记录）

输入 `sm` 首选是「三面」(freq 1350)，而非「什么」(freq 67128，高 50 倍)。

根因（**已验证**）：`coverBonus` 只算**连续公共前缀**。
- 「三面」双拼码 `sjmm`，与 `sm` 共同前缀 `s` → cover = 1/2×999 = 499
- 「什么」双拼码 `ufme`，与 `sm` 共同前缀 0 → cover = 0，只能靠简拼路径拿 1000

`sm` 本质是**两个音节的首字母**（s+m），不是连续前缀。
`coverBonus` 无法表达这种「跨音节首字母」的覆盖关系 —— **这是设计缺陷，不是参数问题**。

我曾试图用「短输入时收窄精确匹配优势」来修（exactBonus 600/1000 分档），
**已证伪**：「三面」走的是非精确分支，改 exactBonus 对它无效。改动已回退，
不留无效代码。正确解法需让 coverBonus 识别简拼（音节首字母序列匹配），
工程量较大，**留待用户实测确认这是否是真实痛点后再做**。

对照证据：搜狗最强项正是简拼容忍度（`nss`→你试试），见 00-research.md §6。
所以这条大概率是真痛点，但我不再凭猜测改排序。

### 2026-08-23 小鹤双拼规则错误（用户是多年小鹤用户）

#### 致命 bug：零声母用错了方案的规则（已修 + 已固化回归）

原实现：`aa/ad/aj/ah/ac` + `ee/ew/ef/eg` + `oo/oz`
—— 即「零声母 = 韵母首字母 + 韵母键」，**这是自然码/微软双拼规则，不是小鹤**。

小鹤规则：**统一用 `o` 引导**。

实测证据（修复前）：
```
oa od oe of oh or ow oq ov  →  全部出「哦」（落空）
oz                          →  恰好撞对（欧）
```

修复后 12 个零声母全对：
```
oa→啊  od→爱  oj→按  oh→昂  oc→奥  oe→鄂
ow→诶  of→恩  og→恩格斯  or→而  oo→哦  oz→藕
```

零声母组词实测 10/10（词首词尾都正确）：
安全 ojqr · 安排 ojpd · 安慰 ojww · 而且 orqp · 爱好 odhc ·
恩惠 ofhv · 治安 vioj · 一般 yibj · 欧洲 ozvz · 额外 oewd

→ **这是最严重的一条**：小鹤用户打「安」「爱」「而且」都是日常高频，
  零声母全废等于第一分钟就用不下去。而我此前所有测试用例**恰好全是非零声母词**
  （你好/我们/中国/明天…），所以 28 条断言全绿却掩盖了这个硬伤。

→ 教训（**已验证**）：测试用例的**覆盖盲区**比断言数量更致命。
  按「规则维度」设计用例（零声母/翘舌/介音/儿化…），不能只按「常用词」堆。

#### 根因：Info.plist 缺 ComponentInputModeDict + 两个键写错

| 问题 | 原值 | 正确值 |
|---|---|---|
| **缺整个键** | 无 `ComponentInputModeDict` | 必须有，否则系统完全不注册 |
| 键名前缀错 | `tsInputMethodCharacterRepertoireKey` | `tsInputModeCharacterRepertoireKey` |
| 值类型错 | `= 2`（整数） | `= ["Hans"]`（字符串数组） |
| 类型值错 | `TISInputSourceType = TISTypeKeyboardInputMode` | 无 input mode 时该值无效，应删 |

`ComponentInputModeDict` 是**系统注册输入法的关键**：它声明具体输入模式，
缺了系统就不把它列进「键盘 → 文本输入 → 添加」，用户根本找不到。

#### 修法依据：取本机能正常工作的开源 IMK 输入法为对照标本

不靠记忆、不靠猜。Context7 无 IMK 资料，改用**本机实证**：
`/Library/Input Methods/Squirrel.app`（鼠须管，开源 RIME 前端，正常工作）。

按此重写后，5 项关键结构与 Squirrel 完全一致，签名有效，
**`open` 后进程首次真正跑起来（PID 77829）**。

### 2026-08-24 整句切分（多字连打）— 用户报「不能多字连打」

#### 根因：引擎缺整句切分这个**架构级能力**

原实现只会「拿整串查词典」，词典没这个组合就退化成最长前缀：
```

nihcwomf（你好我们）→ 只出「你好」
vidcwoyc（知道我要）→ 只出「知道」
```
而用户实际姿势是「一口气打一句、空格上屏」—— 所有成熟输入法的默认交互。

这不是 bug，是**从未实现的功能**。而它正是我在 §7 调研 McBopomofo 时
记为「第一条技术点」的东西 —— **调研了没落地**。

#### ★ 打分模型：McBopomofo 的公式在本项目**实测无效**（已证伪）

McBopomofo 用 `log10(fscale^(字数-1) × freq)`，fscale=2.7。直接照搬失败：

```
路径A 我是+中国  = 11.573
路径B 我是+中+过 = 16.459  ← 胜出，但是错的
```

根因：路径分是**相加**的，词数多的路径凭空多加一项 `log10(freq)`（约 5 分）。
而 fscale 加权项在**总字数相同**时两边贡献几乎一致，抵不掉这个偏差。

实测把 fscale 从 2.7 一路调到 1000，「我是中国」**始终**输给「我是+中+过」
（单字「中」27万、「过」11万，词频本身就极高）。
→ **这是「分数相加」的结构性偏差，不是参数问题，调参无解。**

也试过固定词数惩罚：两条路径词数只差 1，惩罚同时削减双方，需惩罚 > 4.89 才翻转，
那会过度压制正常切分。同样无效。

**采用方案**：`log10(freq) + 成词奖励 × (字数-1)`，奖励值由**真实词库 10 例 DP 实测**定出：
```
bonus=0/2 → 1/10 正确    bonus=4 → 3/10    bonus=5 → 5/10
bonus=6   → 8/10         bonus≥7 → 10/10
```
取 **8**（比临界值 7 留一档余量，防词库更新后落回临界）。

#### ★ 性能：分段计时纠正了我的错误猜测

初版 20 键单次查询 **8.24ms**，被我加的性能门禁拦下（上限 5ms）。

我先猜是 DP 里的字符串拼接，改成切片 + 缓存后 → **7.67ms，几乎没变**。
于是加分段计时，数据直接纠正了我：
```
segmentSentence        0.011 ms   ← 切分本身极快
searchFlypyProgressive 7.647 ms   ← 占 93%
searchPinyin(整串)      0.001 ms
```
慢的**不是新代码**，是 `searchFlypyProgressive` 里的 `byFlypy` **全表扫描**
（十几万个键）。此前没暴露：短输入前缀命中多，400 条上限能早退；
长输入命中少 → 退不了 → 扫完全表。

**修法取舍**：不重构 `searchFlypyProgressive`（它功能正确，短输入断档全靠它，
改它风险大于收益），只在**切分已给出高质量结果时不调它**。
结果：**8.24ms → 0.017ms（快 484 倍）**。
