## 3. 同类标杆拆解（≥3 个，少于 3 个不算完成）

> ⚠️ 本节数据来自 GitHub API 实测 + 官方文档直读。
> 主流商业输入法（搜狗/微信/苹果原生）的实测**尚未完成**，见「调研日志」待办。

| 产品 | 怎么解决这个问题 | 强在哪 | 短板 | 我们的差异 |
|---|---|---|---|---|
| openfly (MIT代码, 1.1k★) | 复刻 v9 官方小鹤，三段式授权隔离风险 | 授权处理最规范，词库开源 | 作者已放弃维护，词库停在 v10.9z；非纯 MIT | 我们不碰官方码表，走自备路线保持纯 MIT |
| 墨奇音形 rime-shuangpin-fuzhuma (MIT, 1037★) | 自造辅助码方案，不依赖小鹤官方码表 | 纯 MIT 可商用，基于雾凇白霜词库 | 不是小鹤音形，键位需重学 | 我们默认小鹤双拼，兼容其用户肌肉记忆 |
| rime-crane 凇鹤 (GPL-3.0, 466★) | 整合雾凇拼音 + 小鹤双拼/音形 | 开箱即用，词库质量高 | GPL 传染性，需装 RIME 全套 | 我们是独立 IME，不要求用户学 RIME 配置 |
| rime-fast-xhup (LGPL-3.0, 369★) | 小鹤双拼+鹤形辅助码，含置顶/删词/降频 | 功能最全（词条置顶、强制删词） | 依赖 RIME，配置复杂 | 我们主打常用语，不做重度定制 |
| RIME 生态整体 | custom_phrase.txt 做自定义短语 | 高度可定制，跨平台 | 门槛极高，普通用户装不明白 | 我们的差异应是「零配置」而非「可定制」 |

### 标杆给的启发

- **授权是这个领域的真实门槛**：4 个高星项目用了 4 种不同 license，全都在处理小鹤码表的版权问题。这不是我们独有的困难。
- **RIME 系全部要求用户懂配置** —— 如果「零配置开箱可用」成立，这是真差异点。
- **没有一个项目以「常用语」为核心卖点** —— 需查清是需求小还是难做（Unknown 高，阻塞定位）。
- openfly 作者转投星空键道，说明**小鹤音形生态本身在萎缩**，把它当核心 feature 的战略价值需重估。

## 6. 商业输入法竞品拆解（2026-08-23 补，来源见各条）

> 调研范围按用户指定：微信输入法 / Gboard 中文 / 搜狗输入法，其余不管。

### 三家横向对比

| 维度 | 微信输入法 | Gboard 中文 | 搜狗输入法 |
|---|---|---|---|
| 最强项 | 无广告 + 跨端剪贴板同步 | **双拼智能纠错**（错字灰显、实时修正） | **词库 + 首选命中率**（简拼容忍极高） |
| 自定义短语 | 独立 App 内设置，可自定义输入码 | 用户词典→个人词典，可批量导入(分块≤5000) | **最强：缩写码+内容+排序号，txt 导入导出 + 直接编辑 Phrases.ini** |
| 双拼含小鹤 | ✅ 支持，路径浅 | ✅ 原生 6 种方案 | ✅ 4 种方案 + **自定义键位映射** |
| 词频学习体感 | **弱**（高频抱怨「没词频老要手动选」） | 无国产式「越打越准」 | **强：手动选两次就上首位** |
| 致命短板 | 体积（104MB→228MB，mac 报 1GB+） | 中文词库弱、无云输入 | **广告与流氓行为**（卸载残留弹窗、候选栏广告） |

### 已验证的关键事实（附来源）

- 微信输入法隐私政策 1.4 明确「常用语、个人词典不会上传」（[隐私政策](https://z.weixin.qq.com/article/privacy)）；
  但换机助手/多端同步需过云，官方未解释边界 → **存疑待核实**
- 微信输入法 `diushi` 打不出「丢失」—— **纠错优先于精确匹配**，完全匹配词被挤出首行
  （[小众软件论坛](https://meta.appinn.net/t/topic/64231)，机制推理为社区推测非官方）
- 谷歌拼音输入法 Windows 版 2018-06 已彻底关停，**不应作为参考对象**；Gboard 从未在中国区上架
- 搜狗云输入官方历史数据：长句准确率 61%→84%（2010 年代数据，仅说明机制）
- 搜狗支持**直接编辑 Phrases.ini** —— 这是小鹤双拼辅助码/音形挂接的通用手法（[sogou-flypy](https://github.com/fanqi/sogou-flypy)）
- 搜狗掉份额主因是广告：卸载后仍弹广告、静默装 `biz_helper.exe`、擅改系统快捷键
  （[什么值得买 904 条评论汇总](https://post.m.smzdm.com/p/a3mnlmwd/)）

### 查不到（不猜）

微信输入法常用语条数/字数上限 · 微信候选排序官方机制 · Gboard 个人词典官方上限 ·
搜狗自定义短语上限官方数字 —— 四项只找到疑似 SEO 站或社区推理。

### 可直接借鉴的设计点（按对本项目的价值排序）

1. **搜狗三字段短语模型**：`缩写码 + 内容 + 排序号` + txt 导入导出 + 可直接编辑配置文件。
   三家中唯一让高级用户能**版本化管理**短语的设计 —— 与本项目「数据是我的、可 git、可脚本」定位完全一致。
   → 本项目当前缺 **排序号**（同码多短语无法定序）。
2. **可见的即时词频学习**：「手动选两次就上首位」是用户判断输入法聪不聪明的唯一直觉指标。
   → 本项目有 `learn()` 但**与新覆盖度排序的交互未设计**（已在待验证清单）。
3. **纠错不得覆盖精确匹配**（微信反面教材）：精确匹配候选必须在首行有位置，纠错只能补位不能挤位。
   → 本项目 baseScore 精确 2000 / 非精确 1000 的分档设计**已符合**此原则，属无意中做对。
4. **Gboard 双拼纠错 + 错字灰显**：把不确定性可视化，让用户敢盲打。→ 可选增强，非 MVP。
5. **微信删除键三向手势 + 全键盘长按移光标**：编辑态手势代替光标微操，成本低收益高。→ iOS 端可借鉴。
6. **默认隐私 + 增强功能独立开关**：本项目天然满足（纯本地、无网络）。

### 反向问题的答案（补 §4.6）

**有没有人做过「常用语为核心」的输入法？** 三家商业输入法**都有**自定义短语功能，
但都是**附属功能**而非核心卖点，且搜狗做得最深（三字段+配置文件）。
结论修正：不是「没人做」，而是**没人把它当主卖点** —— 因为对大众是低频需求，
对特定人群（重复输入长文本者）是高频需求。**(a) 自用工具定位下这恰好成立。**

**同行是不是在撤退？** 谷歌拼音 Windows 版已关停（2018）；搜狗因广告掉份额；
微信输入法在接收搜狗流失用户。商业侧在洗牌而非萎缩。
开源侧（RIME 系）活跃但门槛高。

## 7. 同形态开源标杆：McBopomofo（2026-08-23 补，**最高参考价值**）

> 用户要求调研日文/台湾输入法 + 国内开源标杆。实际最有价值的发现是 McBopomofo ——
> 它与本项目**形态完全相同**：Swift + macOS IMK + 自研引擎 + MIT + 单人维护。
> 它的技术选择就是我们的参考答案。

### 基本事实（已验证，GitHub API + 源码直读）

| 项 | McBopomofo | PhraseKey（本项目） |
|---|---|---|
| 语言 | **Swift** | Swift ✅ 同 |
| 平台层 | **macOS IMK** | macOS IMK ✅ 同 |
| License | **MIT** | MIT ✅ 同 |
| star | 818 | — |
| 活跃度 | 2026-08-08 仍在推送 | — |
| 架构 | Swift(UI/状态机) + ObjC++/C++(引擎) | 纯 Swift |
| **有 `algorithm.md` 完整算法文档（938 行）** | ✅ | ❌ 我们没有 |

→ **结论：自研引擎不是重复造轮子**。同形态项目存在且活跃，说明这条路可行。
→ **但它有完整算法文档，我们没有** —— 这是可直接补的差距。

### 关键技术点（已验证，直读 algorithm.md 与源码引用）

#### ① 整句最优路径用 DAG 最短路径（`reading_grid.cpp:216` walk()）
把候选组成有向无环图（Node→Vertex，相邻节点连边），拓扑排序后求最高分路径。
**对照本项目**：我们只做单点候选排序，没有整句路径优化。
→ 这解释了「连续打字手感」为何是待验证项 —— 我们缺整句视角。

#### ② 用户词分数调整：`topScore + epsilon`（`McBopomofoLM.cpp:120`）★ 最有价值
```cpp
// 多音节用户词：直接用（分数 0 = 最高）
// 单音节用户词：分数设为「主词库最高分 + epsilon(1e-9)」
```
**原理**：单音节用户词若给绝对最高分，会导致多音节词永远无法胜出
（「丼」压死「动作」）。故只给「刚好超过词库最高分」的分数。

→ **直接解答本项目「用户词典自学习与新排序如何交互」这个未设计问题**：
  学过的词不应给绝对高分，而应给「刚好超过同层最高分」。
  本项目当前 `learn()` 是直接提 freq，属于粗暴方案，有压死长词的风险。

#### ③ 词频用对数 + 长词加权（fscale = 2.7）
```python
freq = log10((2.7 ** (字数-1)) * count / norm)
```
长词按 `2.7^(n-1)` 加权 —— 长词天然更该被选中（Max-Match 启发）。
零频次按 0.5 次处理，避免 log(0)。

**对照本项目**：我们已用对数压缩词频（修 `min(freq,999)` 硬截断时改的），
方向一致 ✅；但**没有长词加权系数**，我们的「词长」只作为末级 tiebreak。
→ 可借鉴：把词长从 tiebreak 提升为带系数的加权项。

#### ④ 词库用二分查找 + 数据必须预排序（ParselessPhraseDB）
词库文件预排序，运行时二分查找，不建内存索引 → 内存占用极低。
**对照本项目**：我们建了内存索引（+90.9MB）。
→ iOS 内存受限场景下，二分查找方案可能优于内存索引。**待评估，非当前必需。**
